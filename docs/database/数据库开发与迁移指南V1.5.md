## 1. 文档目标

本文档用于指导 `stock_realtime` 的数据库开发、迁移、保留规则、废弃规则和验证方式。

它要回答：

1. 当前数据库哪些是真值
2. 哪些对象保留，哪些对象废弃
3. 未来迁移应该遵循什么原则
4. 如何保持日线历史真值不被破坏

## 3. V1.5.2 数据模型原则

### 3.1 主事实层

- `realtime_quotes`：秒级盘中事实层
- `kline_minute`：统一分钟事实层，`period` 区分 `1/5/15/30/60`
- `kline_daily`：日线真值层，历史只增不删
- `daily_basic`：日度基础指标层，设计上与 `kline_daily` 同键对齐，承载 Tushare `daily_basic` 指标

### 3.2 业务表

- 股票池、成员、板块、计划、持仓、笔记、标签等属于业务表
- 业务表要支持审计、版本化、可追溯

### 3.3 日志表

- `job_runs` 记录作业生命周期
- `data_quality_log` 记录数据质量、源错误和异常事件

### 3.4 迁移原则

- 日线历史不允许破坏性重建
- 分钟/秒级链路可在兼容前提下重构
- 新结构优先通过 migration 和兼容视图落地
- 任何删除都必须确认是历史过渡对象，而不是当前真值层
- 日度基础指标应独立进 `daily_basic`，不再继续混塞进 `kline_daily`
- `kline_daily` 后续保留窗口按 `>= 2020-01-01` 收敛，不影响 `realtime_quotes` / `kline_minute` 的现有窗口口径

### 3.5 `daily_basic` 设计口径

- 表名：`public.daily_basic`
- 定位：与 `kline_daily` 同键对齐的日度基础指标超表
- 来源：Tushare `daily_basic`
- 时间列：`trade_date`
- 目标形态：Timescale hypertable

首批字段与单位：

- `turnover_rate`：换手率，单位 `%`
- `share`：股数类基础指标，单位 `万股`
- `market_cap`：市值类基础指标，单位 `万元`

当前完成事实：

- `public.daily_basic` 已建表
- 已转为 hypertable，时间列为 `trade_date`
- collector 已具备按 `trade_date` / 日期区间同步 `Tushare daily_basic` 的最小能力
- 当前已完成 `2020-01-02` 到 `2026-04-08` 的历史同步

## 4. Timescale 兼容方向

V1.5.2 设计本来可兼容 Timescale 思路；当前主线已实际完成 Timescale 基础迁移，但本文档仍保留兼容原则，避免把“现状”与“后续演进”混写。

建议方向：

- 行情类表可按时间序列特征规划为 hypertable 方向
- 日级/分钟级聚合可通过 continuous aggregate 或等价批处理方式实现
- 压缩、分区、保留策略需与数据保留期限一致

当前完成事实：

- `realtime_quotes` 已作为秒级 hypertable 生效
- `kline_minute` 已作为统一分钟 hypertable 生效
- `kline_daily` 已作为日线 hypertable 生效
- 未来若调整 chunk、压缩或连续聚合，应另起迁移说明，不要回写成 current-state

## 6. 迁移步骤建议

1. 先确认当前真实表结构与数据范围
2. 再写 migration 方案
3. 再补验证脚本
4. 再写回滚说明
5. 最后更新 current-state 与 API / design 入口

## 7. 验证标准

每次数据库变更至少验证：

- 主事实表仍可读
- `kline_daily` 历史行数未损坏
- 迁移后查询能返回正确字段
- 数据质量日志和作业日志正常

## 8. 与 current-state 的衔接

- current-state 记录当前真实表与链路
- 本文档记录 V1.5.2 数据库开发原则
- current-state 优先于设计草案
- Timescale 完成事实也应优先写入 current-state，再回填本文件的原则说明
- `daily_basic` 已完成真实库落表与历史回灌核验；后续变更应同时更新 current-state 与 runbook
